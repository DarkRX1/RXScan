# Privacy scrub report (Phase 1)

Date: 2026-10-19
Baseline commit: `8fdbe82905953d2de47dc0a44b41d6083f7610d1` (v1.2.1, `master`)
Baseline test result: `cargo test --all-targets` -> **1348 passed, 0 failed, 0 ignored**

This report records what was searched, what was changed, and what was
deliberately left alone. Matched values are shown only as truncated SHA-256
prefixes. The full values were never written to any tracked file, to this
report, or to the quarantine manifest.

## Scope

Searched every git-tracked file (651 at baseline) for:

- maintainer identity: name/handle variants, absolute home paths, host and
  prompt strings, personal contact addresses, repository-identity metadata,
  platform signing identifiers, timezone/locale/first-person hints;
- development-side identity: agent and model names, `Co-Authored-By` and
  similar trailers, session artifacts, editor backups, local tool configs;
- secrets and real-world data: API keys, tokens, cookies, private keys,
  webhook URLs, non-reserved public IPs, non-reserved phone numbers, and
  non-reserved email addresses;
- embedded metadata in every tracked PNG and SVG, plus the incoming icon pack.

## Permanent guard

| File | Purpose |
| --- | --- |
| `scripts/privacy_gate.sh` | Operator-facing POSIX `sh` scanner over tracked files. Generic patterns only; contains no project-specific or literal deny terms. Exits non-zero on any finding. |
| `scripts/privacy_gate.allowlist` | Reviewed exceptions, keyed on the **value digest**, never on the path. |
| `tests/privacy_gate.rs` | The same policy enforced natively in Rust on every OS in the CI matrix, with no new dependency. Nine tests, including one that fails the build if the two implementations drift apart and one that confines wildcard exceptions to the gate itself. |
| `.gitignore` | `privacy-denylist.local.txt` is ignored. |
| `.github/workflows/ci.yml` | A dedicated `privacy-gate` job, so a red privacy lane blocks merge independently of the build matrix. |

`privacy-denylist.local.txt` is loaded by the script when present and is never
committed. The committed gate is fully effective without it.

### Why exceptions are keyed on the value digest

An earlier path-only allowlist would have suppressed every finding in a file
to clear one known fixture. Keying on the SHA-256 prefix of the matched value
means clearing `tests/graph_phase1.rs`'s reviewed PEM header leaves the file
fully watched: planting a *different* private key there still fails the gate.
This behaviour is asserted by test and was verified by hand.

### The gate scans itself

Once `scripts/privacy_gate.sh` and `tests/privacy_gate.rs` became tracked, the
gate immediately reported 24 findings inside its own source: the regex
literals, and the synthetic samples the detectors are proven against. A
secret scanner that cannot hold its own vocabulary is either useless or has to
be silenced wholesale.

The resolution is deliberately narrow. Structural exceptions use a `*` in the
id and digest columns, and
`wildcard_exceptions_are_limited_to_the_gate_itself` fails the build if a
wildcard ever names any file other than the gate's own two. Adding a `*` entry
for `src/tls.rs` was tried and correctly failed the build. Without that test,
the easiest way to make the gate green would have been to sprinkle wildcards
across the tree, which is exactly the shortcut this guard removes.

One report line was reworded rather than allowlisted: the history report
mentioned absolute Windows user paths in prose, which tripped the same
detector. Documentation should not need a privacy exception.

### Detector self-tests

A gate that cannot fail is worthless, so `every_detector_fires_on_a_synthetic_sample`
and `reserved_and_structural_values_do_not_fire` assert each detector fires on
its own synthetic sample and stays quiet on reserved values. These caught three
real defects during development: a `private_key` pattern that never matched
because `grep` read its leading `-` as an option flag; a `public_ip` reserved
check that treated all of `192.0/16` and `203.0/16` as reserved rather than
just the documentation `/24`s; and a `phone` detector that scanned for ten
consecutive digits and so never matched a separated number.

The two implementations were also cross-checked by planting a ten-payload
probe line in a tracked file: both reported **9 findings with identical
digests**, and both correctly skipped the reserved documentation IP and the
fictitious phone number in the same line.

## Verification

### Correction: the earlier Phase 1 clippy claim was a false pass

The previous revision of this section reported only the shell gate and the
privacy-gate test. It did **not** report a clippy run, and no clippy result
from that phase can be relied upon. The clippy check reported as passing was a
**false pass** for two compounding reasons:

- **It never re-linted anything.** Clippy printed `Finished` in 0.15s straight
  from cache, without recompiling or linting the changed code. A sub-second
  clippy run after an edit means the run is not evidence of anything.
- **It was the wrong toolchain.** The run used the default local toolchain
  (`rustc 1.99.0`). CI pins **1.85.0** (`.github/workflows/ci.yml`). A green run
  on any other toolchain is not evidence about the pinned one.

`digest()` in `tests/privacy_gate.rs` was therefore never verified. Reproduced
against the pinned toolchain, `3c615cd` fails:

```
error: use of `format!` to build up a string from an iterator
  --> tests/privacy_gate.rs:79:5
  = note: `-D clippy::format-collect` implied by `-D warnings`
exit code 101
```

The cause was `out.iter().take(8).map(|b| format!("{b:02x}")).collect()`,
which allocates a `String` per byte. It now appends into one buffer via
`std::fmt::Write`. The two forms are byte-identical: both produce 16 lowercase
hex characters of the leading 8 SHA-256 bytes. `scripts/privacy_gate.allowlist`
was **not** touched to accommodate this.

To prove the clippy invocation genuinely lints this file rather than trusting
its exit code, the bug was temporarily reintroduced after the fix landed:
clippy then failed with the same `format_collect` error and exit code 101. The
passing run below is therefore known to have compiled and linted the changed
code, not to have short-circuited on cache.

Two further figures in the previous section were stale, carried over from the
pre-phase commit `8fdbe82`:

- `8 passed` was wrong. The committed `tests/privacy_gate.rs` at `3c615cd`
  contains **9** tests, not 8.
- `651 tracked files` was the count at `8fdbe82`. The phase added five tracked
  files, so the committed count is **656**.

change of even one hex character would silently re-label every reviewed
exception; `no_unreviewed_privacy_findings_in_tracked_files` remains the
authoritative check, and the known-answer vectors are a redundant guard
against a future refactor.

### Second review: a non-reserved address, and what the wildcard hides

A follow-up review found that `tests/privacy_gate.rs` shipped a literal
belonging to the `/24` block immediately above `203.0.113.0/24`. RFC 5737
reserves only `192.0.2.0/24`, `198.51.100.0/24` and `203.0.113.0/24`, so the
next block up is real routable space and that value should not ship.
Following this report's own convention, the address is referred to by digest
rather than quoted:

```
public_ip  tests/privacy_gate.rs  sha256:bc4159863dbc68b4
```

The file contained that literal twice, and the two cases are not equivalent:

| Line | Context | Action |
| --- | --- | --- |
| 745 | `digest_matches_known_sha256_vectors`, the lowercase/width sample list | replaced with a reserved `203.0.113.55` |
| 562 | `every_detector_fires_on_a_synthetic_sample`, the `public_ip` fixture | **cannot** be replaced; see below |

Line 745 only feeds a value to `digest()`; the detector never sees it, so a
reserved address is fine there and the literal is gone.

Line 562 is the fixture that proves the `public_ip` detector fires at all, so
it **must** be non-reserved. This was verified rather than assumed: putting a
reserved `203.0.113.55` in that slot and running the test produces

```
detector `public_ip` failed to fire on its own synthetic sample
test result: FAILED. 0 passed; 1 failed; exit 101
```

because `ip_is_reserved` filters reserved values out and the detector is left
with nothing to match. A reserved address cannot be used to prove that a
reserved-value filter is correct. **A public-IP detector self-test cannot be
written without one non-reserved address**, so this literal is a deliberate
requirement of the test, now marked with a comment at the call site. It is a
string in a detector self-test and is never contacted by any code path. Every
other file touched in this phase was scanned for non-reserved literals using a
mirror of the detector's own `ip_is_reserved` logic; the line 562 fixture is
the only one that remains.

### The wildcard exempting `tests/privacy_gate.rs`

The allowlist entry exempting the gate's own test file reads, verbatim:

```
*|tests/privacy_gate.rs|*|the privacy gate's own self-tests: this file defines the detector patterns and the synthetic samples they are proven against
```

The allowlist was **not** modified by this commit. Whether to tighten or
retire this wildcard is a separate maintainer decision.

It matters because a wildcard suppresses *every* detector for that path, not
just the synthetic samples the entry describes. Re-running the gate with
`allowed()` forced to fail, so the exemption is bypassed and nothing else is
changed, shows the ten findings the wildcard hides in that one file. A patched
copy of the script kept outside the repository was used for this; no tracked
file was modified:

| Detector | Line | Digest | What is actually there |
| --- | --- | --- | --- |
| `email` | 709 | `4022aae8fc2a4629` | the planted-leak canary address |
| `forge_token` | 545 | `1db61e13c133f7d9` | synthetic forge-token fixture |
| `home_path` | 535 | `53a8fcca9845a83e` | a `/home/` operator-path fixture |
| `home_path` | 536 | `cf05319ae9007aa7` | a `/Users/` operator-path fixture |
| `home_path` | 735 | `53a8fcca9845a83e` | the same value, as a known-answer digest vector |
| `home_path` | 745 | `53a8fcca9845a83e` | the same value, as a digest-formatting sample |
| `phone` | 563 | `48c1cea5f658e895` | a NANP-formatted phone fixture |
| `private_key` | 537 | `8bcac7908eb95041` | bare PEM header fixture |
| `public_ip` | 425 | `ad754b3cdaad9067` | out-of-range rejection fixture |
| `public_ip` | 562 | `bc4159863dbc68b4` | the real routable address described above |

Nine of those ten are the gate's own vocabulary and are exactly what the
allowlist entry claims to cover: synthetic patterns, canaries and known-answer
vectors that exist so the detectors can be proven. The tenth, line 562, is the
one real routable address, and it is the one the wildcard is currently the only
thing standing behind.

Quoting the values rather than their digests was attempted in an earlier draft
of this section and the gate immediately reported seven findings against it,
which is the detector set doing its job on its own documentation. This section
therefore carries digests only, as the rest of the allowlist does.

**A privacy-gate PASS is therefore not, on its own, evidence about
`tests/privacy_gate.rs`.** The gate reported `0 findings across 656 tracked
files` while this file was carrying a non-reserved address, because the file
was never examined. Two consequences follow for any future tightening: every
row above needs either a digest-keyed entry or a rewrite to reserved
vocabulary, and the line 562 fixture needs a reviewed entry specifically, since
no reserved substitute exists.

### Standing rule

Never record a clippy or gate result from a run that did not compile the
changed code. Pin the toolchain, and treat a suspiciously fast clippy run as
a failure to verify rather than a success. A green gate run is likewise not
evidence about any file a wildcard exempts.
