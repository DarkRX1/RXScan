# RXScan entity icons (74 types)

Offline, dependency-free icon set for the RXScan graph view. All icons are original
drawings generated by script in a design session; there is no third-party icon source
and no network content. Everything is bundled — icons ship in `app/assets/icons/` and
are loaded from the local API or inlined into exports, never fetched from a CDN.

## Provenance

Placed at the repository root as `rxscan-icons/` by the maintainer (DarkRX) on
purpose. Original drawings, generated by script; no third-party icon source. The
quarantined "unknown provenance" label was the correct instinct without context; this
document is the context. The root `rxscan-icons/` directory is intentionally NOT
committed — the maintainer removes it. The committed copy lives at
`app/assets/icons/`.

## Location

`app/assets/icons/` (covered by the existing `app/**/*` packaging include in
`Cargo.toml`; no packaging change required).

```
app/assets/icons/
  manifest.json
  glyphs/            74 monochrome 24x24 glyphs (currentColor) + rxscan-sprite.svg
  tiles/light/       74 colored 64x64 entity tiles (light theme)
  tiles/dark/        74 colored 64x64 entity tiles (dark theme)
  placeholders/      avatar-placeholder.svg, screenshot-placeholder.svg
```

PNG renders are deliberately NOT copied: PNG export is a dependency-free software
rasterizer that draws shape/color glyphs directly, so it needs no PNG assets and
leaving them out protects binary size.

## Encoding rules

Type is never encoded by color alone: every type has its own glyph, and glyph plus tile
shape together encode the type. Color (ramp) is a secondary, theme-aware accent.

- `glyphs/*.svg`: monochrome 24x24 glyphs using `currentColor` — for inline use and
  the `rxscan-sprite.svg` (`<symbol id="rx-NAME">`).
- `tiles/light/` and `tiles/dark/`: 64x64 colored entity tiles — light and dark theme
  variants; follow `rxscan.css` tokens where the GUI needs exact theme parity, falling
  back to the tile SVGs.

## Labeling rules

Icons and labels never raise or imply confidence (stored values pass through
unchanged). Attribution category icons — `hacker`, `threat-group`, `terrorist`,
`botnet`, `sanctions`, `law-enforcement`, `watchlist` — are entity CATEGORY markers
and must only be applied from stored evidence, never from inference:

- show the source and the evidence ("listed on <named official list>",
  "attributed by <report>") and the confidence, using the same evidence chain as every
  other node
- wording in panels and reports: "listed or attributed by <source>"
- a username, domain, or person must never be auto-labeled terrorist, hacker, or
  threat-group from heuristics, name matching, or free-text strings
- these labels are secret-masked and scope-gated like all other exports
- the automatic entity-to-icon mapping (`src/graph_icons.rs`) asserts none of these
  attribution icons appear heuristically; they can only be shown under Phase 5 rules
  (a stored record carrying a named source, confidence above zero, and an evidence
  reference). If no such stored record exists in the data model, the icons stay unused.

Real screenshots, favicons, or profile images must come from stored evidence and go
through secret masking; fetching them is an opt-in, scope-gated transform.

## Tests

- `tests/icon_pack.rs`: SVG safety test over every shipped SVG (no `<script>`,
  `<foreignObject>`, `<image>`, event-handler attributes, external `href` or
  `url(...)`, per-file size cap) and the manifest parity test (manifest entries and
  shipped files match exactly — no orphans, no missing; every category non-empty).
  Fails if any file is added later that violates these rules.
